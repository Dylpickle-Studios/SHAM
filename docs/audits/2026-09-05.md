# Project audit — 2026-09-05

Audited SHAM 1.2.0 at `e11690a`, including the existing uncommitted system-health changes. The initial audit did not change application code. This report supplements the older root audit report.

**Result: eight actionable findings: two critical, three high, and three medium.** The critical ratings describe failures of the documented control-plane-to-agent security boundary and require authenticated agent access or an authorized deployment path; they are not unauthenticated dashboard exploits. The static-file disclosure is reachable by unauthenticated site visitors.

## Remediation follow-up

All eight findings have been addressed in the working tree. Workload environments now use private env files; Compose volume policies and named-volume checks reject host-backed or unmanaged resources; hidden files are blocked before optimization; OIDC transactions require a browser cookie; and backup health uses the persisted status values. `qs` is updated to 6.16.0.

Restore keeps the data mount in place, journals top-level swaps and rollback progress, and pauses the Runtime Agent while stopping SHAM-owned workloads. The maintained `tar` parser validates archive metadata and safe in-tree links, and backup creation uses that same validator. Runtime Agent identity and restore work directories are preserved/excluded as appropriate. Updated operating instructions describe the restore coordination and Compose environment contract.

Follow-up validation: 314 unit tests passed, 10 browser workflows passed, the deployment/private-listener integration tests passed, and the expanded backup recovery drill passed with an archived dependency symlink and the health endpoint. Syntax, lint, and type checks pass with the original lint warnings cleared. Production dependency audit reports zero vulnerabilities. Docker and the historical baseline remain unavailable, so the container-volume smoke test added to CI and the historical upgrade drill were not run locally. The new smoke script's stage/restart/verify flow was also checked against an isolated native server.

The findings and references below describe the original audited state.

## 1. Critical — caller environment can select the agent's executable

References: [runtime-agent/docker.js:48](../../runtime-agent/docker.js#L48), [runtime-agent/docker.js:213](../../runtime-agent/docker.js#L213), [runtime-agent/docker.js:248](../../runtime-agent/docker.js#L248), [src/config.js:204](../../src/config.js#L204).

`containersRun` validates environment variable syntax, then supplies those variables to the Docker CLI process itself. `runTool` merges them over the agent's operator environment. The default executable is the relative name `docker`, so caller-supplied `PATH` can select an executable in the shared writable data directory. Compose operations also pass caller environment into the CLI.

An authenticated agent caller that can write shared data can execute arbitrary code with the agent's Docker-socket authority. This defeats the documented isolation even though no generic shell RPC is exposed. Other CLI configuration variables also need separation from workload variables; using an absolute executable alone is insufficient hardening.

**Reproduced:** wrote a harmless executable named `docker` into a temporary directory and called the exported `containersRun` operation with `env.PATH` pointing there. It returned `AUDIT_CALLER_SELECTED_EXECUTABLE` as the container ID. No Docker daemon or real container was used.

**Fix:** execute trusted absolute tool paths with an agent-owned environment. Pass workload values through a securely created env file or another mechanism that cannot configure the agent process. For Compose interpolation, explicitly prevent caller values from controlling executable lookup, Docker configuration, plugin loading, and process-loader behavior. Add an RPC-level regression test using an injected `PATH`.

## 2. Critical — named-volume options bypass the Compose host-mount restriction

References: [src/sites/runtime.js:100](../../src/sites/runtime.js#L100), [src/sites/runtime.js:132](../../src/sites/runtime.js#L132), [runtime-agent/docker.js:151](../../runtime-agent/docker.js#L151).

The shared validators reject service mounts with `type: bind` and top-level resources with `external: true`, but do not constrain volume `driver_opts`. A named volume using the local driver can specify `type: none`, `o: bind`, and `device: /`. Its service mount still has `type: volume`, so it passes both validation layers while requesting the host root through the Docker daemon.

This permits a submitted Compose project to access host files, with the exact impact depending on container privileges and host permissions. It also invalidates the assertion that a compromised control plane cannot request arbitrary host mounts. Docker documents that volume driver options are passed through to the driver: [Compose volume reference](https://docs.docker.com/reference/compose-file/volumes/).

**Reproduced:** both `validateComposeProjectPaths` and `composeRuntimePolicy` accepted a configuration with a service mounting the above named volume at `/host`. No host mount was executed; daemon-level exploitation remains untested.

**Fix:** allow only agent-controlled named volumes with approved drivers/options and enforce project-scoped resource names. Validate the complete normalized configuration before execution. Include driver-backed bind mounts and explicit unmanaged volume names in rejection tests.

## 3. High — optimized static delivery exposes hidden files

References: [src/sites/delivery.js:315](../../src/sites/delivery.js#L315), [src/sites/delivery.js:333](../../src/sites/delivery.js#L333), [src/validation.js:467](../../src/validation.js#L467).

The compression/minification middleware serves eligible files before `express.static` applies `dotfiles: 'deny'`. Its path checks enforce containment but allow dot-prefixed files and directories. Compression is enabled by default. A JSON file inside a hidden directory therefore becomes public despite the later deny policy. Minification similarly affects supported HTML/CSS/JavaScript files.

**Reproduced:** used the actual static app with dummy content at `.private/credentials.json` and compression enabled. An unauthenticated GET returned `200 AUDIT_PRIVATE_CONTENT`.

This does not establish disclosure of every dotfile: eligibility depends on extension and the enabled optimization path. It does establish exposure of hidden JSON and other supported assets under the site root.

**Fix:** apply one public-file access policy before every delivery path, including optimized assets, precompressed sidecars, and fallback handlers. If `.well-known` needs an exception, make it explicit. Test hidden files/directories with compression and minification enabled and disabled.

## 4. High — restore cannot replace the configured Docker data mount

References: [src/backup-restore.js:212](../../src/backup-restore.js#L212), [src/backup-restore.js:225](../../src/backup-restore.js#L225), [Dockerfile:50](../../Dockerfile#L50), [docker-compose.yml](../../docker-compose.yml).

Restore stages a sibling of `DATA_DIR`, then renames the entire data directory to a rollback sibling. In the recommended container configuration, `DATA_DIR` is `/data` and the app runs as `node`. Creating `/.data-restore-stage-*` fails because `/` is not writable. Even with permission to stage there, `/data` is a mount point and cannot be renamed as an ordinary directory.

Thus the primary documented deployment mode cannot complete in-app backup restore. This is a source/configuration finding; a live container reproduction was unavailable. The integration restore test passed because it uses a normal temporary directory under `/tmp`.

**Fix:** design restore around a replaceable subdirectory inside the persistent mount, or a recoverable swap of its contents, keeping stage and rollback state on that volume. Coordinate the Runtime Agent and control plane so neither writes to restored state during the operation. Add a restore drill with a real mounted `/data` and the image's unprivileged user.

## 5. High — successful backups can contain entries the restore verifier always rejects

References: [src/operations/configuration.js:400](../../src/operations/configuration.js#L400), [src/operations/configuration.js:487](../../src/operations/configuration.js#L487), [src/backup-restore.js:116](../../src/backup-restore.js#L116).

Backup creation archives the data tree with normal tar link handling and verifies only that the archive can be listed. Restore rejects every symbolic link and hard link. Deployed Node dependencies commonly contain relative executable symlinks in `node_modules/.bin`, and backups do not exclude those directories. Git-managed source can also contain links.

Such archives can be recorded as `success` with the detail “Archive integrity verified,” yet can never pass restore validation. This is separate from the Docker mount issue and also affects native installations.

**Reproduced:** a local archive containing `sham.db`, a regular file, and one ordinary relative symlink was rejected with `Backup archive contains a link or special filesystem entry, which cannot be restored safely.` Source review confirms creation does not apply that rejection before marking success.

**Fix:** define a consistent archive format and use the restore validator during backup creation. Either safely support bounded in-tree links or explicitly exclude/reconstruct reproducible dependency artifacts and document the resulting backup contract. Do not blindly dereference arbitrary links. Test an actual Node deployment with installed package binaries through backup and restore.

## 6. Medium — OIDC state is not bound to the initiating browser

References: [src/oidc.js:165](../../src/oidc.js#L165), [src/oidc.js:179](../../src/oidc.js#L179), [src/server.js:755](../../src/server.js#L755), [src/server.js:809](../../src/server.js#L809).

The authorization flow stores state, nonce, verifier, and redirect URI in a shared database row. It sets no browser-specific login cookie and the callback checks no browser/session binding. An attacker with an eligible IdP account can initiate authorization, intercept their own unused callback URL, and induce a victim to navigate to it. SHAM accepts the attacker's valid state/code and replaces the victim's browser session with the attacker's account.

PKCE and nonce validate the authorization exchange but do not tie this callback to the browser that began it. The impact is login CSRF/session swapping, not authentication as the victim.

**Reproduced:** against a mocked IdP with a locally generated RSA signing key, `beginAuthorization` followed by `completeAuthorization` accepted the attacker identity with no browser-binding input. Route review confirms there is no additional binding at the HTTP layer. No external IdP was contacted.

**Fix:** associate state with a short-lived, random browser cookie or pre-login session, verify it before consuming/exchanging the code, and clear it after completion. Use cookie attributes compatible with the configured callback method. Add a two-browser test proving that one browser cannot complete the other's transaction.

## 7. Medium — the new health panel reports successful backups as errors

References: [src/operations/observability.js:33](../../src/operations/observability.js#L33), [src/operations/configuration.js:487](../../src/operations/configuration.js#L487).

The new uncommitted `systemHealth` implementation expects backup status `completed`; backup creation persists `success`. Consequently every successful latest backup is marked `error`, its completion time is suppressed, and the overall health becomes an error. Running backups are also classified as errors.

**Reproduced:** a row with `status: 'success'` and a completion timestamp produced a check with `status: 'error'`, detail `success at 2026-09-05 12:00:00.`, and `lastCompletedAt: null`.

**Fix:** use the persisted `success` status, explicitly distinguish running and failed backups, and share the status definition between producers and consumers. Verify no-backup, running, success, and failed states.

## 8. Medium — production lockfile contains a vulnerable qs release

Reference: [package-lock.json:2397](../../package-lock.json#L2397).

The production lockfile resolves `qs` 6.15.3. The live npm advisory query reports two moderate advisories for that package: [bracket-key comma parsing](https://github.com/advisories/GHSA-x5fp-wj9c-mxmx) and [attacker-controlled isBuffer](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g). The latter lists 6.16.0 as patched. This is one vulnerable package, not two independently vulnerable installed packages.

No exploitable SHAM request path for either advisory was established. The application uses `express.urlencoded({ extended: false })` and no direct `qs.stringify` call was found in application source; package presence should not be presented as demonstrated application denial of service. The existing high-severity audit gate does not block these moderate advisories.

**Fix:** refresh the compatible transitive lockfile resolution to a patched release and rerun checks, behavioral tests, and the advisory scan. Avoid an unrelated blanket dependency upgrade.

## Coverage and remediation order

The review covered authentication/session/API-token handling, OIDC and WebAuthn code, route authorization, upload/file containment, static and proxy delivery, deployment/runtime policy, agent RPC execution, backup/restore, update/plugin boundaries, operations/health, browser rendering paths, dependency metadata, container configuration, and CI/release checks. This was a broad source and behavioral audit, not an exhaustive proof of correctness or a production penetration test. Live Cloudflare, Pangolin, certificate issuance, remote backup providers, and external identity providers were not exercised.

Prioritize the agent environment and Compose volume failures together with static hidden-file disclosure. Next repair and test both restore failures in the actual container deployment. Then fix OIDC browser binding, health status handling, and the dependency resolution.

Existing strengths include a passing behavioral/browser baseline, checked archive paths, password hashing and session revocation, explicit administrator gates for Docker configuration, signed update support, and temporary-data integration tests. Those controls do not cover the specific gaps above. Type checking also has a material limit: 18 source files contain `@ts-nocheck`, including several authentication, route, deployment, and restore modules.
